## 1. Purpose

deckcheck is an open-source linter for LS-DYNA keyword decks (`.k`, `.key`, `.dyn`). It finds structural
mistakes before the solver runs, through three front doors on one engine: a command line (M1), a VS Code
extension (M2) and an MCP server for AI agents (M3).

The goal is adoption by other analysts. Install counts and real users are the measure of success, not the
number of checks.

## 2. Context and non-goals

- Open parsers already exist (pydyna, dynars, dynakw, lsdyna-mesh-reader, lsdyna-parser). None keeps source
  positions, resolves every include form, and checks references correctly. That is the gap, together with editor
  tooling and an agent interface, none of which exist for LS-DYNA decks.
- **Decision history.**
  - 2026-10-28, option A: build on dynars' rules. M0 said **no-go**: 62 of 68 errors false, and `*INCLUDE_PATH`
    ignored.
  - Then route B1: keep dynars' parser, own the meaning. Dropped the same day: dynars' tokenizer itself drops a
    blank title card and mis-splits `_ID` cards, so the defects sit in the layer B1 meant to keep.
  - A half-day reconnaissance of pydyna (Ansys, MIT) followed. It reads blank titles and `*PART_INERTIA` correctly,
    but it keeps no source positions, has no reference checks, ignores `*INCLUDE_PATH`, reformats on write, and
    costs ~5.5 s to import plus heavy dependencies (Docker, DPF, pandas).
- **Decision 2026-10-28, route B1′ (Chintan).** deckcheck has its own **reader for structure and positions
  only**: blocks, cards, lines, columns and includes. **Keyword meaning comes from pydyna's field database**:
  field layouts, option cards (e.g. `_ID`, placed `pre`) and reference types (e.g. `nsid → SET_NODE`). The database
  is extracted at build time into a data file shipped with deckcheck. Neither dynars nor pydyna is a runtime
  dependency.
- The earlier rule "never write a new full parser" becomes: the reader never interprets keyword semantics on its
  own. Every meaning comes from the extracted data, and a keyword the data does not cover passes through untouched.
- M0 measurements, the torture decks and the LS-DYNA referee carry over as M1's test harness (`docs/m0-assessment.md`).
- Non-goals for version 1: physics checks (units, timestep, hourglass, contact defaults), editing decks, running
  the solver, any GUI beyond the editor.
- Legal: the name and branding never use "LS-DYNA" (Ansys trademark), only "for LS-DYNA" descriptively. Keyword
  documentation is written by us or taken from data whose license allows reuse; the keyword manual is never
  copied.

## 3. Bracketing (version 1)

| | |
|---|---|
| Ceiling | Hover documentation and checks for every keyword in the manual, as LS-PrePost does |
| Target | Correct cross-reference and column checks for the ~30 keywords that make up most crash models; other keywords pass through untouched |

## 4. Architecture

```text
deck files ─► reader ─► blocks + cards (file, line, columns) ─► index ─► rules ─► diagnostics ─► front doors
                ▲                                                 ▲                              (CLI, VS Code, MCP)
          include resolver                              keyword data (extracted from pydyna)
```

| Unit | Does | Depends on |
|---|---|---|
| Include resolver | Follows `*INCLUDE`, `*INCLUDE_PATH`, `*INCLUDE_PATH_RELATIVE` and `*INCLUDE_TRANSFORM` (with its id offsets) in LS-DYNA's search order; detects cycles. Returns the file tree with each `*INCLUDE` line. | file system |
| Reader | Splits each file into keyword blocks (name, options such as `+` and `_TITLE`/`_ID`, line) and cards (line, raw text). Skips `$` comment lines; **keeps blank lines as cards**. Detects free (comma) format per card and long format (`+` suffix, `*KEYWORD LONG=`). `*PARAMETER` substitution happens in the field reader (moved in M1b: it needs field positions). Never interprets a keyword's meaning. | file text |
| Keyword data | One data file generated by `tools/extract_keyword_data.py` from a pinned `ansys-dyna-core`. For each keyword: cards → fields (name, type, offset, width), option cards and their placement, and reference fields → target kind. Also which keywords *define* an entity of which kind (`*PART`, `*PART_INERTIA`, `*ICFD_PART` …). MIT attribution in `NOTICE`. A hand-written overrides file corrects or extends entries the data gets wrong. | build time only |
| Field reader | Applies the keyword data to a block's cards: card alignment (option cards, repeated cards), field values by column span, or by position in free format. Substitutes `*PARAMETER` values where a field holds `&name` (`deckcheck.params`; expressions and scoped parameters are UNKNOWN). Evaluates pydyna's card conditions and lengths with a whitelisted evaluator (`deckcheck.conditions`); cards left after the layout start another instance. Stops a block as `unread` where it can't decide. Yields typed values with file, line and column span. | reader, keyword data |
| Index | Per entity kind: definitions (through the definer table `data/definers.toml`) and references, each with location, using the data's link types (including sign-encoded ids such as a negative curve id, where the data marks them) and `*INCLUDE_TRANSFORM` offsets as LS-DYNA applies them per kind. A kind is **uncertain** where deckcheck can't see all of its definitions or uses (an unresolved family member, an unread block, an unknown parameter, an unrefereed offset, an unfollowed include); rules stay silent on it. | field reader |
| Rules | DC001–DC006, each a function over the index (DC003 over the field reader's problems and the reader's cards, DC004 over the include resolver's problems). | index, reader |
| Diagnostics | Record: file, line, column span, severity, code, message, related locations. Plus the run's coverage: what was not checked and why (unread blocks, unknown parameters, uncertain kinds, kinds outside DC005's audited set). | nothing |
| Front doors | Format diagnostics and coverage. Contain no checking logic. | diagnostics |

Error handling:
- A card that won't parse produces one diagnostic, and the run continues.
- A keyword the data does not cover passes through untouched. It defines nothing and references nothing, and no
  check fires on it. This is the main defence against false alarms. The price: a reference *into* such a keyword's
  ids could look dangling, so DC001 counts as error only for target kinds whose defining keywords are all covered.
- A missing include file is reported (DC004), and the rest of the deck is still checked.

## 5. Version 1 checks

**Three classes of finding (Chintan, 2026-10-29).** The tool gives the engineer every fact it can establish and
lets them decide:
1. **LS-DYNA rejects it**: an error; the run would stop.
2. **LS-DYNA accepts it, but the effect is surprising or there is none**: a warning that states the fact (DC006;
   DC002 for duplicates LS-DYNA accepts).
3. **It looks wrong but is deliberate** (user-defined materials, dummy definitions, a team's workaround or policy):
   the tool can't know intent, so the engineer marks it. Inline suppression and a config file (M4) and rule packs
   (M7) serve this class.

Which class a pattern falls in is decided by LS-DYNA on a torture case, never assumed. Open cases go in the
edge-case register (§12).

| Code | Check | Severity |
|---|---|---|
| DC001 | Dangling reference: a field points at an ID that is not defined (e.g. `*PART` material 99, no `*MAT 99`). When an include is missing, the message says the ID may be defined there. | error |
| DC002 | Duplicate ID: two definitions of the same entity kind with the same ID; the related location is the other definition | error where LS-DYNA rejects the duplicate; warning naming the definition LS-DYNA uses where it accepts it (decided per kind by M1d's LS-DYNA tests) |
| DC003 | Value or format problem: a value that is not of its field's type, or a card containing a tab (LS-DYNA misreads tab-separated cards; M0 torture `tabs`). Also cards past a keyword's layout. Decided by LS-DYNA in M1d: two values in one comma-separated slot are read correctly (`m1d_mixed_free`), so mixed format is not a finding; a value overflowing its fixed field is a silent misread (`m1d_overflow_node`: node id 123456789 read as 12345678 at x = 95.0), reported in M1 only where the spill makes a value not of its type, since telling a spill from two full-width values needs every field of the card read (M4). | warning |
| DC004 | `*INCLUDE` problem: a missing file or a circular include | error |
| DC005 | Unused definition: a material (MAT), section or hourglass control that nothing references. M1 covers only these three kinds, after an audit that every field referring to them is linked (`Index.used()` is a lower bound otherwise); other kinds are listed as not checked. | warning |
| DC006 | Accepted but no effect: a reference LS-DYNA does not check, to an ID that is not defined (e.g. `*BOUNDARY_SPC_SET` with a missing node set: accepted, and the constraint applies to nothing). Which references belong here is decided per keyword by LS-DYNA tests; the rest stay under DC001. | warning |
| DC000 | deckcheck itself could not read a block: one diagnostic, the block's kinds listed as not checked, the run continues; the message asks for a report | warning |

Users can suppress a code with `--ignore DC005` (repeatable) in M1. Inline suppression comments and a config
file come in M4.

What deckcheck could not check (unread blocks, unknown parameters, uncertain kinds, kinds outside DC005's set) is
never a diagnostic. It is reported as coverage, separately (§6).

## 6. Front doors

- **M1, command line:** `deckcheck MAIN.k [MAIN2.k ...] [--format text|json] [--ignore CODE ...] [--version]`.
  Includes are followed from each main deck; several main decks are checked as separate models.
  - Text: one line per diagnostic, `file:line:col  severity  code  message`, sorted by file and line, paths relative
    to the working folder. Then a count (`3 problems (2 errors, 1 warning)`), then a **Not checked** footer listing
    each gap and its reason, with locations. The footer always shows; `--ignore` does not hide it.
  - JSON: `{"version": 1, "diagnostics": [...], "not_checked": [...], "summary": {...}}`. Each diagnostic has `file`,
    `line`, `column`, `end_column`, `severity`, `code`, `message`, `related`. Lines and columns are 1-based,
    `end_column` exclusive (the editor and language-server convention). Field names are fixed within version 1; a
    breaking change bumps `version`.
  - Exit codes: 0 no errors (warnings and not-checked items do not fail); 1 at least one error; 2 deckcheck could not
    run (main file missing, bad arguments). A failure inside one block is one diagnostic and the run continues.
    `--ignore` removes a code from the output and the exit code.
  - Not in M1: colour, progress output, config files, SARIF.
- **M2, VS Code:** a Python language server (pygls) behind a thin TypeScript client. Diagnostics as squiggles,
  hover over field names, go-to-definition on IDs across includes. Published to the VS Code Marketplace and
  Open VSX.
- **M3, MCP server:** tools `lint`, `explain_keyword`, `find_references`, `get_card` and `set_field`. `set_field`
  re-runs the linter and refuses any edit that adds an error.

M2 and M3 designs are detailed in their own specs when reached. This spec binds M0 and M1.

## 7. M0 parser bake-off

After the option A decision, M0's question is no longer "which parser" but **"can deckcheck stand on dynars?"**
pydyna is measured only as the fallback.

dynars passes M0 when, on the full corpus:
1. It parses every deck without crashing, within the memory cap.
2. Its four rules produce zero unexplained findings (each finding is either a real defect in that deck,
   recorded, or a dynars false alarm, counted).
3. Every finding's line, after our correction, points at the right keyword block.
4. `set_field` round-trip: parse, write without edits → byte-identical; one edit → only that field's bytes differ.
5. It handles long format, free (comma) format and `*PARAMETER` in the torture decks.

If dynars fails 1 or 2 on decks that matter (VIVA+ or the vehicle model), stop and return to option B with
pydyna; that is a spec change, decided with Chintan.

M0 output: a written assessment (publishable on its own), the false-alarm count per rule, and the go/no-go
recorded in this spec.

**M0 result (2026-10-28): NO-GO for option A.**
- dynars' parser and edits mostly pass (criteria 1 and 4), with two parser defects: a blank-title `*PART` is
  dropped, and `*PART_INERTIA` is not indexed.
- Its reference rules and include resolution fail: 62 of 68 errors are false, and VIVA+ loads 2 of 18 files
  because `*INCLUDE_PATH` is ignored.
- The Yaris (CCSA) ran with 0 errors, but it could not be refereed by LS-DYNA Student (too large).
- Recommended route B1: dynars parser plus deckcheck's own reference and position layer.

See `docs/m0-assessment.md`. Route chosen by Chintan 2026-10-28: B1, then revised the same day to **B1′** (own
reader, pydyna's keyword data) after the reconnaissance in section 2. A formal M0b on pydyna was skipped by
decision: the reconnaissance had already answered it. dynars' defect reports can still be offered upstream.

## 8. Test corpus

| Tier | Decks | Stored |
|---|---|---|
| 1. Breadth | ~20–30 official LS-DYNA example decks across keyword families. As run in M0: 35 decks from the LS-DYNA Student install's `documentation/` folder (dynaexamples.com returned 503), read in place | Local only; never committed (see `docs/corpus-terms.md`) |
| 2. Real-world | VIVA+ human body model (LGPL v3, downloaded at test time) and the CCSA 2010 Toyota Yaris (local only; README asks for acknowledgement in publications) | Never committed |
| 3. Torture | 15 tiny decks from M0, one quirk each, every one checked against LS-DYNA Student. M1 adds one per new reader case | Ours, committed |

External decks are listed in `tests/corpus/manifest.toml` with URL and sha256, and never committed. A changed
upstream deck fails the hash check instead of being tested silently.

Tests:
- Each rule has a tiny deck containing its mistake, which it must catch.
- Each rule must report zero diagnostics on every corpus deck, unless the finding is verified as a real defect
  in that deck and recorded as an expected finding.
- Verification by class: findings LS-DYNA rejects are refereed by LS-DYNA. LS-DYNA accepts unused definitions, so a
  DC005 finding is verified by confirming its ID appears nowhere else in the deck text, then recorded as expected.

## 9. Project setup

- Location `D:\AI_Projects\deckcheck`, local git. A public GitHub repo at the M1 release, only with Chintan's
  explicit yes.
- License: Apache-2.0 (explicit patent grant helps corporate adoption).
- Python core. Packaging via `pyproject.toml`; `pip install deckcheck` gives the core and CLI, with extras
  `deckcheck[lsp]` (M2) and `deckcheck[mcp]` (M3).
- Layout: `src/deckcheck/{includes.py, reader.py, keywords.py, fields.py, conditions.py, params.py, definers.py, index.py, rules/, diagnostics.py, cli.py, data/}`,
  `tools/extract_keyword_data.py`, `tests/{rules/, torture/, corpus/manifest.toml}`, `bakeoff/` (M0 measurement
  scripts and results), `editors/vscode/` (M2), `docs/`.
- Runtime dependencies: none beyond the standard library in M1. `ansys-dyna-core` is a pinned dev/build dependency
  of the data extraction only; dynars stays a dev dependency of `bakeoff/` only.
- CI (GitHub Actions): a fast job on every push (rule and torture tests); a corpus job nightly or on demand
  (download, hash check, zero-false-alarm gate). Run locally with a memory cap.
- CONTRIBUTING.md centres on "add a keyword = add rows to a schema file".
- Later, not in M1: SARIF output for inline pull-request annotations.

## 11. Completion criteria

- **M0 done:** dynars runs on all three tiers; each of the five pass criteria in section 7 is measured and
  written up; the go/no-go is recorded here; the terms for the example decks and CCSA are checked and recorded.
- **M1 done:**
  - The keyword data is checked first: for every keyword involved in M0's seven defects (`_ID` options, ICFD/mesh
    parts, `*PART_INERTIA`, `*BOUNDARY_PRESCRIBED_MOTION_RIGID`, `*CONTROL_IMPLICIT_SOLUTION`, `*DEFINE_TABLE`,
    `*INCLUDE_TRANSFORM`, `*RIGIDWALL_PLANAR`, `*INITIAL_VELOCITY_GENERATION`), the extracted layout and links
    match the deck text. Mismatches go into the overrides file, each with its evidence.
  - DC001–DC006 each catch their seeded mistake (`seeded_mistakes`, `crlf_seeded`, `latin1_seeded`, `tabs`,
    `spc_set_none`, and the M1d cases), with exact diagnostics in each case's `expected.toml`.
  - LS-DYNA has decided, on torture cases: which set-taking boundary and load keywords accept a missing set
    (DC006 vs DC001); whether duplicates of PART, MAT, SECTION, CURVE, node set and NODE are rejected or accepted, and
    which definition wins (DC002 severity); whether field overflow and mixed format are silent misreads (DC003 scope).
  - DC005's audit is done for MAT, SECTION and HOURGLASS: every look-alike unlinked field is either linked in the
    overrides file with evidence or recorded as another namespace.
  - `*MAT_USER_DEFINED_MATERIAL_MODELS` is read correctly or reported as not checked, never a false finding.
  - All seven M0 defects pass as ordinary tests: `include_path`, `long_format`, `blank_title`, `part_inertia`, an
    `_ID` case, an ICFD case, and a misread-field case (each LS-DYNA-checked).
  - Every diagnostic points at the data card and field that caused it: line exact and column span exact on all
    torture decks.
  - Zero unexplained diagnostics on tier 1 (refereed by LS-DYNA's input phase), VIVA+ (all 18 files loaded) and the
    Yaris, under a 2 GB memory cap.
  - `pip install` works from a clean environment with no runtime dependencies: a built wheel, installed into a fresh
    venv, runs on a torture deck. The wheel carries the keyword data, `LICENSE` (Apache-2.0) and `NOTICE` (pydyna MIT).
  - The README covers what deckcheck is ("for LS-DYNA", never as the brand), install, usage, both output formats, exit
    codes, the six checks, what "Not checked" means, and known limits (no physics checks, `LONG=Y` not read, large
    models not refereed by LS-DYNA).
  - The package is published to PyPI only with Chintan's explicit yes.
- **M1 progress (2026-10-29): M1a–M1d done.** M1d (checks, CLI, JSON, README, clean install) on branch `m1d`; evidence
  per criterion in `docs/m1d-checks-cli.md` §4. Publishing to PyPI waits for Chintan's explicit yes.

### Edge-case register

Cases where what LS-DYNA accepts may differ from what the engineer meant, and deliberate patterns teams use. Each is
marked tested (by an LS-DYNA torture case) or untested. Nothing is built from an untested entry; M4 (suppression,
model-quality checks) and M7 (rule packs) draw on this list.

| Case | Class (§5) | Status | Where handled |
|---|---|---|---|
| `*BOUNDARY_SPC_SET` with a missing node set: accepted, constraint applies to nothing | 2 | tested (`spc_set_none`) | DC006 |
| Other set-taking keywords with a missing set (`*BOUNDARY_PRESCRIBED_MOTION_SET`, `*LOAD_NODE_SET`, `*LOAD_SEGMENT_SET`, `*INITIAL_VELOCITY`, `*DATABASE_HISTORY_NODE_SET`) | 1 | tested (`m1d_*_set_none`: all rejected, Error 10144) | DC001 |
| Two definitions with the same ID (PART, MAT, SECTION, CURVE, node set, NODE at different coordinates) | 1 | tested (`m1d_dup_*`: all rejected, Errors 10176, 10137, 10173, 10110, 11168) | DC002 error |
| A node defined twice at identical coordinates | 2 | tested (`m1d_dup_node_same`: accepted, no warning) | DC002 warning (deckcheck doesn't compare coordinates) |
| Tab-separated card: silently misread | 2 | tested (`tabs`) | DC003 |
| Value overflowing its field (a 9-digit node id in an 8-wide field) | 2 | tested (`m1d_overflow_node`: accepted, read as node 12345678 at x = 95.0 instead of 5.0, no warning) | not detected yet (needs full-card field reading, M4); DC003 only where the spill makes a value not of its type |
| Two values in one comma-separated slot | none | tested (`m1d_mixed_free`: accepted and read correctly) | not a finding; removed from DC003 |
| `*DEFINE_FUNCTION` id where a curve is expected: rejected (Error 10141) | 1 | tested | DC001 |
| User-defined materials (`*MAT_USER_DEFINED_MATERIAL_MODELS`, variable card count) | 3 | tested (`m1d_umat`: umat41 accepted); deckcheck reads it: MAT 2 defined and used, no finding, nothing unread | read |
| Dummy or placeholder definitions (e.g. a material kept for rigid parts, an unused definition library kept as policy) | 3 | untested | DC005 warning; suppression in M4 |
| Team workarounds and site conventions | 3 | collected as reported | rule packs (M7) |
